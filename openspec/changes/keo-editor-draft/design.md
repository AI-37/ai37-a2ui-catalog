# Решения

## Решение 1. `draftAction` — опциональный пропс, как у двух соседей

Ни нового вида action'а, ни своей формы. У обоих редакторов каталога это уже
один и тот же ключ с одной и той же оговоркой:

```ts
// constructions-editor.ts и lift-editor.ts — дословно одинаково
// Имя action'а автосохранения черновика. Необязательный: без него компонент
// ведёт себя как раньше — наружу уходят только submit и back.
draftAction: z.string().min(1).max(120).optional(),
```

Опциональность — не вежливость к старым эмитентам, а рабочий режим: агент,
который черновик хранить не умеет, просто не присылает ключ, и компонент
остаётся однодействийным.

## Решение 2. Что считается поводом отправить черновик

Канон двух соседей различает два повода, и КЕО берёт оба:

- **правка поля** — дебаунсом: серия правок схлопывается в одну отправку после
  паузы. Константа общая, `CONDITIONS_DRAFT_DEBOUNCE_MS` = 500 мс
  (`renderers/conditions-draft-debounce-ms.ts`), своего числа не заводим;
- **структурная правка** — сразу, без паузы: добавление и удаление помещения,
  «Далее». Ждать здесь нечего — событие единичное, а не серия.

Правка условия (город) идёт по первому поводу: это правка поля, просто поле
живёт в условиях.

## Решение 3. Ответ — снапшот на месте, а не новое сообщение

Теплотех формулирует это прямо
(`spai-teplo-calc/src/handler/handleConstructionsDraft.ts`):

> Ответ — самодостаточный снапшот с ТЕМИ ЖЕ `messageId`/`surfaceId`: клиент
> заменяет сообщение на месте, нового сообщения в треде не появляется. Тихий
> ack без `a2ui` не годится — путь «ход без формы» ведёт к текстовому
> fallback'у, то есть к новому сообщению.

Это ловушка, а не деталь: «ничего не отвечать» на автосохранение выглядит
дешевле всего и даёт лишнее сообщение в треде на каждую паузу ввода.

Ход черновика идёт **без конвейера, LLM и биллинга** — как `lookup:suggest`.
Автосохранение не расчётный ход и платным быть не должно.

## Решение 4. Черновик кладётся как есть

Ни валидации, ни нормализации, ни записи в `calcDoc`. Черновик по определению
дырявый: новое помещение появляется пустым в момент «+ Добавить помещение»,
условия — недозаполненными. Полная перезапись, без слияния с предыдущим.

Формат — тот же, что у `submit`: `{conditions, rooms}`. Два формата на одни и
те же данные разъедутся, и разбирать их пришлось бы дважды.

## Решение 5. Ответ-черновик не пересевает состояние экрана

**Здесь КЕО отличается от соседей, и это главная работа change'а.**

Сегодня:

```ts
// use-keo-editor-next.ts
const propsKey = JSON.stringify([props.rooms, props.roomTemplate, props.conditions]);
if (propsKey !== baseKey) {
  const next = seed(props);
  setBaseKey(propsKey); setState(next); setTouched(new Set()); setReviewed(new Set(next.open));
}
```

Новый снапшот props сбрасывает раскрытие, тронутые поля и счёт просмотренного.
Правило верное для нового сообщения агента — и разрушительное для черновика:
**ответ на черновик по определению приносит новые props**, причём меняется
ровно то, ради чего всё затевалось — подпись климата в `props.conditions`.

Получилось бы так: пользователь выбирает город → через 500 мс уходит черновик →
приходит снапшот → секция схлопывается, метки «изменено вами» слетают, пометки
«просмотрено» обнуляются. Под руками у пользователя.

Правило: **пересев — по новому сообщению, а не по новым props.** Ответ на
собственный черновик снапшотом-заменой (те же `messageId`/`surfaceId`) новым
сообщением не является, и состояние экрана переживает его целиком; из props
берутся только присланные значения и подписи.

Как отличить одно от другого — открытый вопрос 1.

## Решение 6. Подпись условия гаснет только там, где пересчитать некому

Решение 5 change'а `keo-editor-next` гасит `note` условия при правке значения.
Оно остаётся в силе **как поведение без `draftAction`**: пересчитать
действительно некому, и пустая строка честнее неверной.

С `draftAction` пустота становится лишней: подпись обновится ответом. Здесь она
живёт до ответа и заменяется присланной — то есть «Петербург · группа 3»
вместо «Петербург» и вместо неверной «группы 1».

Цена: между отправкой и ответом подпись показывает прежнюю группу — те самые
500 мс плюс round-trip. Принимаем: окно короткое и заканчивается правдой, а не
пустотой.

## Открытые вопросы

1. **Как компонент отличит новое сообщение агента от ответа на свой
   черновик.** `propsKey` этого не различает — он видит только props. Варианты:
   сравнивать не всё подряд, а «значения и структуру» (подписи и `note`
   исключить из ключа); либо считать пересев по внешнему признаку
   (`messageId`/id снапшота), если он доступен рендереру; либо гасить пересев
   на время «свой черновик в полёте». **Дефолт:** исключить из `propsKey`
   подписи и `note` — тогда ответ, меняющий только их, пересева не вызывает, а
   новое сообщение с другими значениями вызывает. Проверить глазами
   обязательно: это ровно тот класс ошибок, который тесты не видят.

2. **Уходит ли черновик при правке, не меняющей документ** — раскрытие секции,
   «просмотрено». **Дефолт:** нет. Черновик про данные; раскрытие агенту знать
   незачем, а лишний ход стоит round-trip.

3. **Что показывать, пока черновик в полёте.** У соседей — ничего.
   **Дефолт:** ничего же; служебный трафик пользователю не показывается
   (канон `/proba/lift-assembly`: приёмка по консоли, не по экрану).
