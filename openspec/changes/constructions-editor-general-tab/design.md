## Context

`ConstructionsEditor` (0.7.0) — экран конструкций одним сообщением; «Исходные
данные» остались отдельной FormCard. Переход между ними — раунд-трип
(`backAction`), из-за чего ввод теряется, тред засоряется, а ГСОП не виден
рядом с чипами Rпр. Change `constructions-editor-draft-save` (0.8.0) закрыл
потерю лишь частично — черновик уезжает только на структурных правках.

Ключевое наблюдение, которое делает объединение возможным: **на момент ввода
вкладки друг от друга не зависят**. Нормативы (ГСОП, Rнорм) считает агент
после submit'а; клиенту они нужны только для чипа, и без них чип просто не
показывается.

Компонент уже доменный: типы конструкций СП 50, λА/λБ, `pol_po_gruntu` в
схеме. Поэтому поля климата вводятся типизированным блоком, а не generic-
механикой поверх FormCard.

## Goals / Non-Goals

**Goals:**

- Один экран — одно сообщение: ввод исходных данных и конструкций без единого
  раунд-трипа.
- Ввод не теряется по построению: терять нечего, пока пользователь не нажал
  submit.
- Город подставляет климат — меньше ручного ввода из СП 131.
- Чип Rнорм либо честный, либо отсутствует.

**Non-Goals:**

- Generic «опция lookup заполняет соседние поля» в FormCard.
- ГСОП/Rнорм на клиенте (коэффициенты `a`/`b` табл. 3 СП 50 не переезжают).
- Третий таб, сохранение выбранного таба между ходами, персист незасабмиченного
  при перезагрузке.

## Decisions

### Решение 1. Табы внутри компонента, а не структурный `Tabs` каталога

Табы рисует сам `ConstructionsEditor`. Альтернатива — ввести в каталог
контейнер `Tabs` со слотами и собрать экран из двух компонентов. Отвергнута:
это отдельный структурный примитив, влияющий на весь каталог, а выигрыш здесь
нулевой — оба таба обслуживает один state и один submit.

Расплата честная: компонент окончательно становится экраном teplo-calc.
Это уже так (типы конструкций, λА/λБ, subtype'ы СП 50 в схеме), так что новых
принципов не нарушается.

### Решение 2. Типизированный блок `general`, а не список `formFieldSchema`

```
general: {
  buildingType: string | null,
  city: {value, label} | null,
  tot: number | null, zot: number | null,
  tn: number | null, tv: number | null,
  condition: 'А' | 'Б' | null,
}
buildingTypeOptions: string[]
cityReferenceId: string
```

Альтернатива — `generalFields: formFieldSchema[]` с произвольными именами:
гибко, но тогда «какое поле опции города в какое поле формы» надо объявлять
пропом-маппингом, то есть тащить в схему generic-механику ради одного
справочника. При фиксированных именах подстановка `tot`/`zot`/`tn` —
внутреннее дело рендерера, ровно как заполнение λ из опции материала.

### Решение 3. Submit ничего не блокирует

`handleSubmit` всегда шлёт `{general, constructions}`. Клиентская валидация с
подсветкой и `validate-constructions.ts` удаляются целиком.

Причина: единственный компетентный валидатор — агент (нормативы, справочники,
согласованность климата и типов). Дублирование правил на клиенте даёт две
расходящиеся истины и мешает ровно тому сценарию, ради которого затевались
табы: заполнить конструкции, не заполнив общие данные. Ответ агента — текстом,
не подсветкой в форме.

Альтернатива — оставить подсветку, но не блокировать. Отвергнута: подсветка без
блокировки читается как ошибка ввода, хотя пользователь просто ещё не дошёл до
поля.

### Решение 4. «Климат тронут» — сравнение снимка props с текущим state

Компонент запоминает `general` из props при инициализации и сравнивает с
текущим состоянием. Отличается хоть одно поле климата (`tot`, `zot`, `tn`,
`tv`, `buildingType`, `city`) → `rnorm` считается протухшим: чипы показывают
`Rпр` без сравнения, сводка «проходит N из M» скрыта.

Альтернативы: считать Rнорм на клиенте по коэффициентам `{a, b}` (чипы всегда
живые, но клиент начинает применять норматив — прямой non-goal исходного
change'а); ничего не скрывать (чипы врут). Выбран самый честный дешёвый
вариант — «нет данных, значит не показываем».

Флаг живёт до следующих props: агент, ответив на submit, присылает
пересчитанный `rnorm` и снимок обновляется.

### Решение 5. `backAction` опционален, а не удалён

На объединённом экране кнопка возврата не нужна, но выламывать обязательные
поля схемы у существующих эмитентов незачем: `backLabel`/`backAction`
становятся опциональными, поведение при их наличии прежнее. Схема при этом
остаётся аддитивной, v2 сохраняется.

### Решение 6. `condition` — во вкладке, top-level проп deprecated

Значение λА/λБ теперь редактируется пользователем, значит его место — в
`general`. Top-level `condition` остаётся начальным значением для эмитентов,
которые ещё его шлют; приоритет — у состояния вкладки, дефолт по-прежнему λБ
(синхронно с сервером).

## Risks / Trade-offs

- **Компонент растёт** → рендерер уже разбит на подфайлы; вкладка общих данных
  добавляется отдельным файлом `constructions-editor-general.tsx`, общий файл
  остаётся оркестратором state'а.
- **Потеря клиентской валидации** → плохо заполненный submit теперь всегда
  доходит до агента, качество ответа целиком на нём. Смягчение: агент отвечает
  перечнем недостающего тем же экраном, а не общим «заполните форму».
- **Длинное сообщение на мобиле** → две вкладки вместо одной формы; активна
  всегда одна, высота не суммируется.
- **`spai-teplo-calc` обязан обновиться синхронно** → до его правки старый
  экран «Исходные данные» продолжает работать как FormCard; компонент с
  `general` просто не эмитится. Схема совместима в обе стороны.
- **Черновик становится шире** → `{general, constructions}` вместо
  `{constructions}`; для агента это перезапись одного слота, объём тот же
  порядок.

## Migration Plan

1. Каталог: minor с `general`, опциональными `backLabel`/`backAction` и снятой
   блокировкой submit'а.
2. `spai-teplo-calc`: сборка `general` в props, обработка `{general,
   constructions}` в submit-хендлере, текстовый ответ о недостающем, вывод
   экрана «Исходные данные» из ротации.
3. Откат — агент эмитит прежние props без `general`: компонент показывает
   единственную вкладку конструкций, кнопку возврата и прежний submit-payload.

## Open Questions

  обсуждения макета; на контракт этого change'а не влияет.
