# design: keo-draft-echo-ack

## Решение 1. Канонический ключ — сортировка пар, а не deep-equal

`keoDocumentKey` сериализует отсортированные пары `[ключ, значение]` условий и
значений каждого помещения. Альтернатива — структурное сравнение распарсенных
документов — дала бы то же самое ценой второй функции сравнения: ключ уже
используется как строка (сравнение, хранение в ref), менять форму API незачем.

`undefined` отбрасывается до сортировки: `JSON.stringify({a: undefined})` даёт
`{}`, и пара `['a', undefined]` в массиве превратилась бы в `null` — ключ со
значением-`undefined` и отсутствующий ключ обязаны считаться одним документом,
иначе появится новый ложный повод для пересева.

Имена помещений и `note` остаются вне ключа — по прежним причинам Решения 5
`keo-editor-draft`.

## Решение 2. Ack — по последнему отправленному черновику, отдельным ref'ом

Guard получает вторую проверку: снапшот, чей документный ключ равен ключу
ПОСЛЕДНЕГО ОТПРАВЛЕННОГО черновика, — это ack, пересев пропускается, даже если
живое состояние уже ушло вперёд (пользователь печатал, пока черновик летел).

Ключ хранится отдельным ref'ом `lastDraftKey`, а не выводится из существующего
`lastDraft`: дедуп отправки различает документы вместе с именами помещений
(полная сериализация), эхо по именам не отличают (Решение 5). Одна
сериализация на обе роли смешала бы два разных отношения эквивалентности.

Сравнение с живым состоянием остаётся второй веткой ack'а: черновик мог ещё не
уходить (первый рендер после перезагрузки), а снапшот-реплей истории обязан
опознаваться и без `lastDraftKey`.

## Граница

Новое сообщение агента, случайно равное последнему черновику, будет принято за
ack — и это корректно: пересев тех же данных ничего не изменил бы, кроме
схлопывания секций. Устаревание `lastDraftKey` не нужно: следующий настоящий
документ от него не зависит — он отличается содержанием.
