# Сравнение вариантов: fetch в компоненте vs A2UI action-канал

Два проработанных варианта доставки подсказок для lookup-поля `FormCard`:

- **Вариант 1** — `arch-option-1-component-fetch.md`: компонент сам делает
  `fetch` на BFF-роут, тот проксирует на REST оркестратора.
- **Вариант 2** — `arch-option-2-action-channel.md`: компонент шлёт A2UI
  `action` тем же каналом, что и submit; агент отвечает `updateDataModel`.

Схема каталога (`type: 'lookup'`, `referenceId`, `minChars`) и UX
(debounce, дропдаун, скрытый input, submit) в обоих вариантах одинаковы —
различается только доставка подсказок.

## Сравнение по критериям

| Критерий | Вариант 1 (fetch) | Вариант 2 (action-канал) |
| --- | --- | --- |
| Маршрутизация справочников (много агентов/сценариев, `referenceId` не уникален) | Нужен внешний механизм: `sessionId`-проброс + резолв на оркестраторе | Решается по построению: `action` несёт `surfaceId`, попадает агенту-владельцу формы |
| Авторизация | Новая цепочка: cookie → BFF-роут → Bearer → оркестратор (по готовому паттерну) | Существующая: тот же канал, что submit |
| Новая инфраструктура | BFF-роут + REST-эндпоинт + владелец контракта | Нет новых поверхностей; хендлер события на хосте |
| Связанность каталога с потребителем | Рендерер знает URL BFF (хардкод или новый конфиг каталога) | Каталог знает только протокольный `dispatchAction` |
| Владение данными поля | Форму описывает агент, данные едут отдельным контрактом мимо него — два источника правды | Владелец формы = владелец данных её полей, один контракт |
| Латентность suggest | ~50–150мс (прямой REST) | ~100–300мс (run-цикл оркестратора) |
| Сложность на хосте | Ниже: обычный REST-хендлер | Выше: хендлер в run-конвейере + соответствие `surfaceId → messageId` |
| Зависимость от внутренностей библиотек | Нет | Есть: семантика `messageId` проверена по исходникам конкретных версий (@ag-ui/client, @copilotkit/react-core v2), а не по документированному API — апгрейд может потребовать перепроверки |
| Replay треда после перезагрузки | Не затрагивается | Требование: ответ — полный самодостаточный снапшот |
| Поведение при недоступности источника подсказок | Тихий fallback | Тихий fallback (одинаково) |

## Рекомендация: вариант 2

Аргументы против варианта 1 — архитектурные, против варианта 2 —
тактические.

У варианта 1 слабые места заложены в конструкцию: маршрутизация
справочников требует внешнего механизма (`sessionId`-проброс — ручное
воссоздание контекста, который у канала уже есть), знание о справочниках
дублируется вне агентов, каталог привязывается к конкретному потребителю,
появляется новая публичная поверхность. Каждый новый сценарий и каждый
новый потребитель каталога усиливают эти точки.

У варианта 2 издержки локальны и не растут с масштабом: латентность
закрывается debounce/`minChars`, требование `messageId` — одно правило на
стороне хоста, зависимость от внутренностей библиотек — риск апгрейда, а
не риск эксплуатации.

## Где рассуждение может быть уязвимо

Точки, на которые стоит смотреть при ревью — контраргумент по любой из
них может изменить вывод:

- **Семантика `messageId`** — проверена по исходникам установленных
  версий, не по публичному контракту. Если апгрейд CopilotKit/AG-UI её
  изменит, вариант 2 потребует адаптации. Смягчение: зафиксировать
  smoke-тест «повторный снапшот с тем же `messageId` обновляет surface».
- **Латентность run-цикла** — оценка ~100–300мс не измерена под нагрузкой;
  если реальный оркестратор даёт заметно больше, UX автокомплита
  деградирует.
- **Оценка «100 агентов/сценариев»** — если по факту справочники общие
  для всех сценариев (один глобальный `materials`), аргумент маршрутизации
  ослабевает, и простота варианта 1 весит больше.
- Возможны варианты, не рассмотренные здесь (например, гибрид: канал
  варианта 2 для маршрутизации + прямой REST для горячих справочников с
  кэшем).
