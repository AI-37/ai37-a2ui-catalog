## Context

ThermalReport уже задал канон read-mostly отчёта: strict-схема, строки
готовые к показу, action-объект {name, label, payload?}, группы исходных
данных с тонами, протокол одной строкой со «Скачать» (после
thermal-report-standard-buttons), CE-канон кнопок, своя группа токенов.
Референс визуала — макет SP-AI «КЕО — 0,42 % при норме 0,50 %».

Отчётная форма модуля КЕО нормирована ГОСТ Р 21.514—2025: табл. А.1
(здание), Б.1 (сводка помещений), Б.2 (коэффициенты расчёта). ГОСТ явно
допускает свою форму представления при сохранении полного состава
параметров — карточка + скачиваемый протокол этому удовлетворяют.

## Goals / Non-Goals

**Goals:**

- Карточка результата КЕО с вердиктом, вариантами исправления и
  трассируемыми исходными данными; повторное использование канона TR.
- Кнопки-действия возвращают агенту структурированный payload
  (`report_recalc {roomId?, window?}` и т.п. — имена не зашиты в схему).

**Non-Goals:**

- Общий «generic calc-report» на замену ThermalReport: секция рекомендаций
  и пер-помещенные статусы доменные; TR уже в проде у teplo-агента —
  обобщение потребует миграции и отдельного решения. Рассмотрено и
  отклонено в пользу отдельного компонента по общему канону.
- Логика соответствия (сравнение e_p с e_н, допуск −10 % по СП 367
  п. А.2.12, ветки прерывистости) — на агенте.
- Рендер протокола в UI (только скачивание).

## Decisions

1. **Схема повторяет структуру TR** (verdict/inputs обязательны, остальное
   опционально, режим по наличию секций, без cross-field refine), но
   отдельным компонентом: секция `recommendations` уникальна.
2. **Карточка рекомендации**: `tone` управляет рамкой/цветом
   (success — зелёная рамка + кнопка действия обычно есть; fail — detail
   danger-цветом, действия нет; neutral — обычная). Наличие кнопки
   определяется только полем `action`, не tone — агент волен сочетать.
3. **Протокол — строка + Скачать** (Blob из `downloadContent ??
   content`), сразу по новому канону — `<details>` не вводим, чтобы не
   повторять миграцию TR.
4. **`rooms[]` — опциональная секция**: супер-MVP считает одно помещение,
   секция появляется при мультипомещенном расчёте; вердикт тогда сводный
   («N из M соответствуют») — формирует агент.
5. **Подпись протокола в фикстурах — «формулы СП 367.1325800 · … шагов»**
   (правка макета: математика — СП 367; СП 52 — только C_N/MF/e_н).
6. **Группа токенов `kr`** с INHERITS (прецедент tr).

## Risks / Trade-offs

- [Дублирование секций verdict/inputs/protocol с TR] → осознанно: канон
  копируется файлами-секциями, общий рефактор (shared report-sections) —
  отдельным change после двух-трёх отчётных компонентов (появится третий —
  insolation-report).
- [Пустой отчёт (только verdict+inputs) пройдёт схему] → как у TR:
  наполнение валидирует агент.
- [Blob-download в хосте spai-ui] → уже проверяется в рамках TR; наследуем
  результат.

## Open Questions

- Нужна ли отдельная секция `checks` (как у TR) вдобавок к рекомендациям —
  в макете КЕО её нет; заложить в схему опционально или добавить позже.
- Состав скачиваемого протокола: только Б.2 или А.1+Б.1+Б.2 одним файлом —
  решает агентская сторона.
