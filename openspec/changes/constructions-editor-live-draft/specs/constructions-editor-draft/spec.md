## MODIFIED Requirements

### Requirement: Правки полей конструкций не запускают автосохранение

Компонент SHALL NOT отправлять `draftAction` в ответ на изменение значений
полей КОНСТРУКЦИЙ — типа конструкции, subtype, названия, толщины слоя,
материала, λ, паспортного Rпр — а также на разворачивание и сворачивание
карточки. Такие правки SHALL уезжать наружу вместе со следующим
`draftAction` либо с `submitAction`.

#### Scenario: Правка поля конструкции без структурного действия

- **WHEN** пользователь меняет название конструкции и толщину слоя
- **THEN** компонент не отправляет ни одного action'а

#### Scenario: Правка поля конструкции перед структурным действием

- **WHEN** пользователь меняет название конструкции, а затем добавляет
  вторую конструкцию
- **THEN** отправляется ровно один action `draftAction`
- **AND** в `context` первая конструкция содержит новое название

## ADDED Requirements

### Requirement: Автосохранение правок условий с дебаунсом

При заданном `draftAction` компонент SHALL отправлять
`dispatchAction({event: {name: draftAction, context: {general,
constructions}}})` после изменения любого поля блока условий — города,
назначения помещений, tв, условий эксплуатации, tот, zот, tн — с дебаунсом:
серия правок SHALL схлопываться в один action, отправляемый после паузы
ввода. Payload SHALL собираться из состояния на момент отправки (последний
ввод побеждает).

#### Scenario: Серия правок — один action

- **WHEN** пользователь подряд вводит tв, tот и zот без пауз длиннее окна
  дебаунса
- **THEN** компонент отправляет ровно один `draftAction` после паузы
- **AND** `context.general` содержит все три введённых значения

#### Scenario: Правки с паузами

- **WHEN** пользователь вводит tв, ждёт дольше окна дебаунса, затем вводит tот
- **THEN** компонент отправляет два action'а `draftAction`
- **AND** второй содержит оба значения

#### Scenario: Выбор города из справочника

- **WHEN** пользователь выбирает город в lookup-поле
- **THEN** автозаполненные климатические поля и город уезжают `draftAction`
  после паузы дебаунса одним action'ом

### Requirement: Кнопки сохранения условий нет

Компонент SHALL NOT рендерить отдельный элемент управления для сохранения
блока условий: автосохранение делает явный коммит условий несуществующим.
Состояние «условия изменены, но не сохранены» SHALL NOT влиять на рендер.

#### Scenario: Ввод в поля условий

- **WHEN** пользователь меняет значения полей условий
- **THEN** никакая кнопка сохранения не появляется

### Requirement: ГСОП и производные видны всегда и обновляются из снапшота

Компонент SHALL всегда рендерить поле ГСОП: значение `general.gsop` из
props последнего пришедшего снапшота, при его отсутствии — прочерк. После
ответа агента на `draftAction` (in-place replace тем же `messageId`)
компонент SHALL отобразить пересчитанные производные (`general.gsop`,
`typeConfigs`) из новых props, при этом значения полей ввода SHALL остаться
локальными (ввод пользователя не затирается).

#### Scenario: ГСОП обновился после ввода климата

- **WHEN** пользователь ввёл tв, tот и zот и дождался draft-ответа агента
- **THEN** поле ГСОП показывает пересчитанное значение
- **AND** введённые значения полей не изменились

#### Scenario: ГСОП не прячется при вводе

- **WHEN** пользователь начал менять климатическое поле
- **THEN** поле ГСОП остаётся видимым (прежнее значение либо прочерк)

### Requirement: Submit отменяет отложенный draft

Нажатие submit SHALL отменять запланированный, но ещё не отправленный
`draftAction` (сбрасывать таймер дебаунса): после `submitAction` компонент
SHALL NOT отправлять draft с тем же состоянием.

#### Scenario: Submit сразу после ввода

- **WHEN** пользователь меняет поле условий и нажимает submit до истечения
  окна дебаунса
- **THEN** уходит только `submitAction` с полным состоянием
- **AND** отложенный `draftAction` не отправляется
