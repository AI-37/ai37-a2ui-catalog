## Context

Каталог v2 (FormCard, ChoiceCard, ConstructionsEditor, LiftEditor,
ThermalReport, …). Паттерн редактора задан LiftEditor: zod-схема в
catalog-schemas, рендерер в catalog-react, локальный state с одним submit,
поля — расширение `formFieldBaseSchema`, метки источника, экспандер
необязательных полей. Референс визуала — два макета SP-AI «Параметры
расчёта» (вариант «предложено агентом» и вариант «из вашего вопроса»).

Нормативная база модуля КЕО: математика — СП 367.1325800.2017 (формула А.1,
алгоритм 8.4.1, схема N1); коэффициенты C_N, MF, e_н и группы районов —
СП 52.13330.2016; форма отчётных таблиц — ГОСТ Р 21.514—2025. Скоуп
супер-MVP (встреча 13.05.2026): одно жилое помещение или кухня, одно окно,
боковое одностороннее освещение, максимум одно противостоящее здание строго
напротив (схема N1), без лоджий.

### Правки к макетам (нормативная сверка)

| Нет ветки «затенение есть» | супер-MVP включает одно здание строго напротив (схема N1) | условная группа полей: расстояние l, фронт a, высота, ρ_ф (допущение 0,5 — ГОСТ 21.514 / практика), этаж |

## Goals / Non-Goals

**Goals:**

- Один компонент собирает документ расчёта КЕО (условия + N помещений) и
  отдаёт его одним submit; редактирование целиком на клиенте.
- Трассируемость каждого значения (метка источника) — требование ТЗ и основа
  колонки «принято системой — проверьте» будущего отчёта.
- Контракт совместим с ГОСТ Р 21.514 (собираемые поля покрывают состав
  табл. А.1/Б.1 для сценария супер-MVP).

**Non-Goals:**

- Расчёт КЕО, интерполяции таблиц, справочники СП/ГОСТ на клиенте — всё у
  агента.
- Схемы застройки N2–N6, несколько разноориентированных проёмов, верхнее
  освещение, двустороннее боковое.
- Черновики/draftAction (по итогам ревью можно добавить по канону CE).
- Агентская сторона — парный change в репозитории агента КЕО.

## Decisions

1. **Документ submit** — `{conditions, rooms: [...]}`; conditions: регион
   (readonly-подпись), rooms[n]: назначение, комнатность, ориентация,
   геометрия (d_п, b_п, h), светопроём (b_o, h_o, количество, h_пд,
   остекление), затенение, умолчания (ρ поверхностей, Δ_ст, лоджия/балкон).
   Плоские значения-строки/числа; форматирование — агент.
2. **Поля описываются расширением `formFieldBaseSchema`** (прецедент
   LiftEditor) — метка, тип, опции, диапазоны, метка источника, подсказка.
   Новой параллельной модели поля не вводим.
3. **Вычисляемые подписи вместо хардкода норм.** Плоскость расчёта и
   положение расчётной точки — из mapping в props
   (`computedNotes: {byPurpose, byApartment}`), пересчёт на клиенте при
   смене назначения/комнатности (аналог `dependentRules` LiftEditor).
   Компонент не знает СП — он знает «ключ → готовая строка».
4. **Ветка затенения — условная группа полей** (`revealBy`: поле-триггер
   «противостоящее здание»). В состоянии «нет» — warning-подпись «опасное
   допущение: не указанная застройка завышает результат» (строка из props).
5. **Валидации — предупреждения, не блок** (канон CE «! проверить»):
   правила приходят из props с параметрами (тип правила + границы), клиент
   вычисляет и подсвечивает. Правило d_п/h₀₁ включает определение h₀₁ от
   агента (см. Open Questions).
6. **Экспандер «Коэффициенты приняты по умолчанию»** — свёрнутые
   редактируемые поля с меткой «допущение»/«предложено»: ρ отделки, MF,
   Δ_ст, лоджия/балкон (прецедент `advanced` LiftEditor).
7. **Своя группа токенов `ke`** с INHERITS на общие (прецедент ce/le/tr).

## Risks / Trade-offs

- [Определение h₀₁ (верх проёма над полом vs над УРП) в правиле п. 9.1.1
  разночтимо между конспектами] → правило параметризуется агентом; сверка по
  PDF СП 367 — на агентской стороне до включения правила в фикстуры.
- [Количество окон > 1 вне супер-MVP] → поле остаётся, значение > 1 даёт
  предупреждение «расчёт по каждому проёму с суммированием — вне базового
  сценария» (строка из props).
- [條ная группа затенения усложняет схему поля] → один механизм `revealBy`
  на компонент, без вложенных условий.
- [Дрейф с формой табл. А.1 ГОСТ (здание целиком vs помещение)] → супер-MVP
  собирает по-помещенно; поля здания (высоты этажей, отметка ±0,000)
  добавятся отдельным change при переходе к полной А.1.

## Open Questions

- h₀₁ в ограничении d_п/h₀₁ ≤ 2,5 (СП 367 п. 9.1.1): от пола или от УРП —
  сверить по PDF первоисточника.
- Значение τ₀/τ₁ для двухкамерного стеклопакета в фикстурах — взять из
  табл. А.8/А.9 СП 367 после сверки (в макете «0,50» без τ₂ сомнительно).
- Нужен ли draftAction (живой черновик) как у CE — решить на ревью демо.
