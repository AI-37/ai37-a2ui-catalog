## ADDED Requirements

### Requirement: Схема props компонента KeoEditor

Каталог SHALL предоставлять компонент `KeoEditor` со strict-схемой props:
`title`, `meta` (строка проекта/норматива), `conditions` (readonly-поля
условий: регион с группой светового климата), `roomTemplate` (описатели
полей помещения по секциям: назначение, геометрия, светопроём, затенение,
умолчания; поля — расширение `formFieldBaseSchema` с меткой источника,
подсказкой, диапазонами), `rooms[]` (значения по помещениям),
`computedNotes` (mapping «назначение/комнатность → подпись плоскости и
точки расчёта»), `validationRules[]` (параметризованные правила
предупреждений), `submit` ({name, label}). Все нормативные значения и
подсказки — готовые строки/числа из props; нормативных таблиц СП/ГОСТ в
компоненте нет.

#### Scenario: Валидная фикстура

- **WHEN** props содержат conditions, roomTemplate, одно помещение
  (жилая комната, Тюмень — группа светового климата 1) и submit
- **THEN** схема принимает объект, компонент попадает в артефакт каталога
  вместе с JSON-схемой

#### Scenario: Лишнее поле

- **WHEN** в props передан не описанный схемой ключ
- **THEN** strict-схема отклоняет объект

### Requirement: Помещения повторяются на клиенте без раунд-трипов

Компонент SHALL поддерживать несколько помещений («Помещение 1…N»):
переключение, «+ Добавить помещение» (значения из `roomTemplate`-дефолтов)
и удаление SHALL выполняться локальным state'ом без dispatchAction; наружу
уходит только один submit «Рассчитать» с полным документом
`{conditions, rooms[]}` в `context`.

#### Scenario: Добавление помещения локально

- **WHEN** пользователь нажимает «+ Добавить помещение» и заполняет поля
- **THEN** ни одного dispatchAction не происходит до нажатия «Рассчитать»

#### Scenario: Submit полного документа

- **WHEN** пользователь нажимает «Рассчитать» при двух помещениях
- **THEN** диспатчится `{event: {name: submit.name, context}}`, где context
  содержит conditions и оба помещения с текущими значениями

### Requirement: Метки источника значений и счётчик в футере

Каждое поле со значением SHALL показывать метку источника (из проекта /
из вашего вопроса / предложено агентом / рассчитано / допущение) в подписи
под полем; правка поля пользователем SHALL переводить метку в «изменено
вами». Футер SHALL показывать сводный счётчик по источникам.

#### Scenario: Допущение помечено

- **WHEN** поле «Отражение фасада ρ_ф» пришло со значением 0,5 и источником
  «допущение»
- **THEN** под полем рендерится метка допущения, поле учтено в счётчике

#### Scenario: Правка пользователя меняет метку

- **WHEN** пользователь меняет «предложенную» высоту подоконника 0,9 на 1,0
- **THEN** метка поля становится «изменено вами», счётчик обновляется

### Requirement: Плоскость и точка расчёта — вычисляемые подписи, не ввод

Компонент SHALL NOT содержать редактируемого поля «рабочая плоскость».
Вместо него SHALL рендериться вычисляемая подпись плоскости и положения
расчётной точки, выбираемая из `computedNotes` по текущим значениям
«назначение помещения» и «квартира» и пересчитываемая на клиенте при их
смене. Тексты подписей приходят готовыми строками (для жилых комнат и
кухонь агент передаёт плоскость пола Г-0,0 по СП 52 Прил. Л, а не УРП 0,8).

#### Scenario: Жилая комната 1–3-комнатной квартиры

- **WHEN** назначение — «Жилая комната», квартира — «1–3-комнатная»
- **THEN** подпись показывает строку из computedNotes для этой пары
  (в фикстуре: «расчётная точка — на полу, 1 м от дальней стены»)

#### Scenario: Смена назначения на кухню

- **WHEN** пользователь меняет назначение на «Кухня»
- **THEN** подпись пересчитывается без dispatchAction (в фикстуре:
  «расчётная точка — на полу, в центре помещения»)

### Requirement: Условная ветка затенения по схеме N1

Поле «Противостоящее здание» SHALL раскрывать при значении «есть» группу
полей затенения (расстояние до здания, длина фронта, высота, отражение
фасада ρ_ф с дефолтом-допущением, этаж расчётного помещения), объявленную
в roomTemplate через `revealBy`. При значении «нет» группа скрыта и SHALL
показываться warning-подпись из props о принятом допущении открытого
горизонта.

#### Scenario: Раскрытие полей застройки

- **WHEN** пользователь выбирает «Есть — здание напротив (схема N1)»
- **THEN** поля расстояния, фронта, высоты, ρ_ф (0,5 · «допущение») и этажа
  появляются локально, без dispatchAction

#### Scenario: Открытый горизонт с предупреждением

- **WHEN** значение поля — «Нет — открытый горизонт»
- **THEN** группа скрыта, под полем показана warning-подпись о допущении

### Requirement: Предупреждающие валидации геометрии из props

Компонент SHALL вычислять правила из `validationRules[]` (в т.ч. отношение
глубины к высоте верха проёма d_п/h₀₁ ≤ 2,5 и h_пд + h_o ≤ высоты
помещения; параметры и текст сообщения — из props) и подсвечивать
нарушенные поля пометкой «! проверить» с текстом правила. Нарушение SHALL
NOT блокировать submit.

#### Scenario: Нарушено отношение глубины

- **WHEN** глубина 5,2 м при верхе проёма, дающем d_п/h₀₁ > 2,5
- **THEN** поля глубины и окна подсвечены warning-пометкой с текстом
  правила, кнопка «Рассчитать» остаётся активной

#### Scenario: Окно выше потолка

- **WHEN** h_пд + h_o больше высоты помещения
- **THEN** соответствующие поля подсвечены пометкой «! проверить»
