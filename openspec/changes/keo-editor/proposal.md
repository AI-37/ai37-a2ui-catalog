# KeoEditor: сбор исходных данных расчёта КЕО одним сообщением

## Why

Модуль КЕО в SP AI стартует со сбора исходных данных (стратегия «3 таблицы»
ГОСТ Р 21.514—2025: А.1 → Б.1 → Б.2, супер-MVP — одно помещение, схема
застройки N1). Согласованы макеты формы «Параметры расчёта», но в каталоге
нет компонента: плоские FormCard фрагментируют чат (доказано лифтами), а
сами макеты содержат нормативные неточности, которые надо зафиксировать и
исправить на уровне контракта props (см. design.md, «Правки к макетам»).

## What Changes

- **Новый компонент каталога `KeoEditor`** (аддитивно, `CATALOG_VERSION` v2):
  общий блок «Условия» + повторяемые помещения («Помещение 1…N»,
  `+ Добавить помещение», удаление) локальным state'ом без AG-UI-run;
  один submit «Рассчитать» с полным документом `{conditions, rooms[]}`.
- **Метки источника значений** у каждого поля (из проекта / из вопроса /
  предложено агентом / рассчитано / допущение) — канон source-note
  ConstructionsEditor/LiftEditor; счётчик источников в футере
  («1 из проекта · 5 из вопроса · 5 предложены агентом»).
- **Нормативные правки относительно макетов** (обоснование — design.md):
  - поле «Рабочая плоскость, 0,8 м» убрано из ввода — плоскость расчёта
    вычисляемая подпись: для жилых комнат и кухонь — пол Г-0,0
    (СП 52 Прил. Л, пп. 187–188), не УРП 0,8;
  - вместо «Кз 1,2» — коэффициент эксплуатации MF (табл. 4.3 СП 52;
    для вертикальных окон жилых MF = 0,83);
  - добавлено поле «квартира: 1–3-комнатная / 4+» и вычисляемая подпись
    положения расчётной точки (СП 52 п. 5.3);
  - раскрываемая ветка затенения по схеме N1 (расстояние, фронт, высота,
    ρ_ф с допущением 0,5, этаж) — в макете ветки «есть здание» нет;
  - добавлены толщина стены Δ_ст и лоджия/балкон (τ₄) в экспандер
    «Коэффициенты приняты по умолчанию»;
  - размер окна — два числовых поля (ширина × высота), не строка.
- **Нормативных справочников на клиенте нет**: e_н, группа светового
  климата, C_N, τ₁/τ₂/τ₄, MF, ρ — готовые значения и подписи в props от
  агента; клиент лишь переключает подписи/наборы полей по правилам из props
  (аналог `dependentRules`/`optionsBy` LiftEditor).
- **Предупреждающие валидации геометрии** (правила и границы из props):
  d_п/h₀₁ ≤ 2,5 для жилых (СП 367 п. 9.1.1), h_пд + h_o ≤ высота потолка,
  диапазоны чисел — подсветка «! проверить», не блок.
- Фикстуры valid/invalid/messages, превью в apps/demo, TS/React/Python-тесты.

## Capabilities

### New Capabilities

- `keo-editor`: контракт компонента — схема props, повторяемые помещения на
  клиенте, метки источника, вычисляемые подписи (плоскость и точка расчёта),
  условная ветка затенения N1, предупреждающие валидации из props, один
  submit с полным документом.

### Modified Capabilities

_(нет — существующие компоненты не меняются)_

## Impact

- `packages/catalog-schemas`: `components/keo-editor.ts` + регистрация
  (`constants.ts`, `catalog.ts`, `index.ts`); `pnpm run export:public`.
- `packages/catalog-react`: `renderers/keo-editor*.tsx/.ts` (паттерн
  LiftEditor: экран/секция/поле/стили/source-note), регистрация в
  `catalog.ts`, группа токенов `ke` с INHERITS на общие.
- `packages/catalog-python`: зеркальная Pydantic-модель + parity-тест.
- `fixtures/*`, `apps/demo` (пример с логером действий), `tests/react`.
- Версия: minor bump (`pnpm run version:bump`) + CHANGELOG.
- Потребители: будущий агент КЕО (модуль SP AI, сборка sp-ai-bundle/keo-calc)
  эмитит компонент и обрабатывает один submit; spai-ui поднимет пакеты.
- **Non-goals**: расчёт КЕО и любые нормативные таблицы на клиенте; схемы
  застройки N2–N6; верхнее освещение; несколько окон в супер-MVP (поле
  «количество» есть, > 1 помечается предупреждением); импорт BIM/IFC.
