# Design — блок подбора в LiftEditorNext

## Context

- Экран собран так: `LiftEditorNext` (a2ui-обёртка, `dispatchAction`) →
  `LiftNextScreen` (разметка: шапка, `Accordion` с секциями «Здание» и
  «Лифт i», подвал) → `useLiftEditorNext` (черновики по методикам, `touched`,
  раскрытие/просмотр секций, дебаунс черновика). Второй потребитель экрана —
  песочница `/proba/lift-assembly`, поэтому получатель состояния приходит
  `sink`'ом.
- Наружу уходит один документ `{method, building, lifts}`: `submitAction` и
  опциональный `draftAction` (`LIFT_DRAFT_DEBOUNCE_MS`). Структурные действия
  (добавить/удалить лифт, сменить методику, «Далее») шлют черновик немедленно,
  отменяя отложенный.
- Доменных знаний о ГОСТ в компоненте нет: состав полей, ряды значений и
  зависимые правила (`dependentRules`) целиком приходят в props. Инвариант
  сохраняем — блок подбора тоже не должен знать ни про Q, ни про Vн.
- Готовый лёгкий канал: `GET /api/agent-resource?resource=<id>&…` оркестратора
  (`spai-chat-backend/src/main.ts:96`) — резолвит `resource` по реестру
  remote-a2a в REST-ручку агента-владельца, форвардит ВСЕ query-параметры с
  user-JWT, ответ passthrough, без биллинга. Прецедент в этом пакете —
  `useLookupSuggest` (debounce + `AbortController` + тихий fallback).
- Режимы лифтов у методик разные: 52941 — `per-lift` (секции «Лифт 1…N»,
  `maxLifts` 10), 34758 — `group` (одна секция, число лифтов `Nl` — обычное
  поле). Вариант подбора при этом всегда означает «n одинаковых лифтов».

## Goals / Non-Goals

**Goals:**

- Как только обязательные параметры здания валидны — показать ранжированный
  подбор, не гоняя снапшот формы через A2A.
- Клик по варианту заполняет лифтовые секции целиком (включая число лифтов) и
  уезжает обычным черновиком — никакого нового канала наружу.
- Список никогда не врёт: показан только пока он соответствует текущим
  значениям полей; гонки ответов отбрасываются.
- Компонент остаётся домен-агностичным: какие поля уходят в запрос и какие
  значения куда кладутся — данные, а не код.
- Любой сбой канала — тихая деградация до нынешней формы.

**Non-Goals:**

- Расчёт подбора на клиенте (Решение 1).
- Блок в старом `LiftEditor` — он заморожен как эталон сравнения.
- Объяснение «почему этот вариант» — текстовые пояснения приходят готовыми
  строками, компонент их не строит.
- Кэш ответов между размонтированиями, пагинация, бесконечный список.
- Биллинг/квоты запроса — забота ручки агента (канон agent-resource: лёгкое
  чтение не тарифицируется).

## Decisions

### 1. Данные — из ручки агента, а не из локального пересчёта

Ядро подбора — TS и могло бы жить в shared-пакете (мгновенный локальный
список), но это был бы второй артефакт с нормативной ГОСТ-математикой:
дрейф версий развёл бы список и итоговый расчёт «Рассчитать». Один источник
истины в агенте важнее; debounce 300 мс + сеть незаметны на фоне ввода.

### 2. Включение — проп `recommend`, а не константа компонента

Без пропа блока нет: старые сообщения агентов не меняют поведения, откат —
удаление пропа, и агент явно владеет тем, у каких методик подбор вообще есть.
`resource` (id ресурса реестра, например `lift-recommend`) и опциональный
`taskId` — в пропе; **путь ручки в проп не выносим**: `AGENT_RESOURCE_ROUTE`
захардкожен константой пакета — агент не должен диктовать браузеру, куда
ходить (то же решение, что у `LOOKUP_SUGGEST_ROUTE`; константа переезжает в
общий файл и переиспользуется обоими каналами).

### 3. Какие поля уходят в query — декларативно, списком `params`

`params: [{name, scope?, required?}]` — имена полей активной методики и экран,
на котором они живут (`building` по умолчанию, `lift` — берётся из первой
лифтовой секции: H0/Nn/dt 52941 живут именно там). Компонент собирает query из
текущих значений черновика по этому списку, ничего не зная про смысл полей.
Альтернатива «слать весь документ» отвергнута: ручка тогда обязана угадывать
методику по составу ключей, а лишние поля (уже введённый лифт) сбивали бы
подбор.

### 4. Формат варианта: отдельно показ, отдельно применение

```ts
type RecommendResourceVariant = {
  id: string;                 // ключ списка/селекта
  title: string;              // «ЩЛЗ ПП-1026ЕН · 3 лифта»
  subtitle?: string;          // «1000 кг · 1,6 м/с · дверь 1200 ЦО»
  notes?: string[];           // «tи 62,00 с», «комфортность отличная», «поток 118,00 %»
  tone?: 'ok' | 'near';       // прошёл ГОСТ / близ-промах
  apply: {
    count: number;                                  // сколько лифтовых секций
    values: Record<string, string | number>;        // поля ЛИФТА
    buildingValues?: Record<string, string | number>; // поля ЗДАНИЯ (34758: Nl)
  };
};
type RecommendResourceResponse = {echo?: Record<string, string | number>; variants: RecommendResourceVariant[]};
```

`apply.count` — сколько лифтовых секций должно получиться, `apply.values` —
значения полей лифта, `apply.buildingValues` — поля ЗДАНИЯ, которые задаёт сам
вариант: у 34758 число лифтов `Nl` живёт на экране здания, а не в секции
группы. Полей, которые сами являются входом подбора, там не бывает — иначе
применение варианта меняло бы запрос. Всё, что видно глазом, приходит готовыми строками:
форматирование чисел, единицы и словоформы комфортности — знание домена, и оно
остаётся у агента. Владелец типов — `catalog-schemas`; агент импортирует их из
`@ai37/a2ui-catalog-schemas`, а не копирует.

Расхождение, которое нужно закрыть в зеркальном change: спека агента
(`recommend-resource`) описывает плоские доменные поля варианта (model, n, Q,
Vн, …) и «клик заполняет Лифт 1». Плоские поля втащили бы в компонент знание
ГОСТ-полей, а «Лифт 1» потерял бы `n` — вариант «3 лифта по 1000 кг»
превратился бы в один лифт. Поэтому контракт — `title/subtitle/notes/apply`, а
число лифтов едет в `apply.count`.

### 5. Применение варианта — как структурное действие

Клик по кнопке карточки или выбор варианта в списке (подтверждения у списка
нет — Решение 10): сборка лифтовых секций (`per-lift`: `count` одинаковых секций, с
клампом по `maxLifts`; `group`: одна секция, `count` игнорируется) + запись
`apply.buildingValues` в секцию «Здание», если они есть → значения помечаются
`touched` → отложенный черновик отменяется и уходит немедленный, как при
добавлении лифта. Пометка `touched` обязательна по двум причинам: `dependentRules`
иначе перетрут h/t123 подставленными по Vн, а подписи источников
(`liftSources`) должны сняться — значение теперь не «из вашего вопроса».
Раскрытая секция после применения — первая лифтовая (пользователь смотрит,
что ему подставили).

### 6. Актуальность — по ключу запроса, эхо как страховка

Ключ запроса = сериализация тех самых значений `params`, из которых собран
query. Ответ применяется, только если ключ совпал с текущим (иначе — молча
выброшен), а `AbortController` гасит предыдущий in-flight. `echo` ручки
проверяется дополнительно и щадяще: числовые значения сравниваются по
`Number()`, потому что нормализация на сервере («17» → 17, «1,6» → 1.6) иначе
объявила бы свежий ответ протухшим. Расхождение по эху — тот же тихий выброс.

### 7. Состояния блока

`hidden` (не все `required` заполнены — блока нет вовсе), `loading` (порог
пройден: дебаунс + запрос), `shown` (варианты есть), `empty` (ответ пустой —
одна строка `emptyLabel`, форма не блокируется), `stale` (значения изменились —
показываем прежний список приглушённым до нового ответа, чтобы блок не прыгал).
Ошибка сети/404/500 → `hidden`: сломанный канал не должен пугать пользователя
красным в форме расчёта.

### 8. Место в разметке — между «Зданием» и лифтами, вне `Accordion`

Блок — не секция: у него нет бейджа, он не участвует в навигации «Далее» и не
считается просмотренным. Ставим отдельным узлом между `SectionItem` «Здание» и
списком лифтовых секций (`Accordion.Root` разрезается на две части либо блок
рендерится сразу после него — см. tasks 3). Карточки — `Card` + `Button`
примитивов, остальные варианты — `Select`; клавиатура и `aria` библиотечные.

### 9. Хук отдельно от разметки

`useRecommendVariants` (дебаунс, отмена, ключ, состояния) — отдельный файл по
образцу `useLookupSuggest`; `LiftNextRecommendBlock` — презентация; сборка
черновика по варианту — чистая функция `applyRecommendVariant(draft, variant,
config)`, тестируемая без DOM. Это же даёт песочнице `/proba/lift-assembly`
работать без сети: хук возвращает `hidden`, если пропа нет.

### 10. У списка выбора нет кнопки подтверждения

> **Снято решением 11:** списка выбора нет вовсе.

Принято при осмотре сборки на `/proba/lift-assembly`. В первом варианте рядом
с селектом стояла кнопка `applyLabel` — как в спеке до этой правки. Глазами
видно, что она лишняя: кнопка обещает шаг, которого нет, и делает строку
«ещё варианты» шире и тяжелее двух карточек над ней, хотя несёт менее важные
варианты.

Отказаться от подтверждения можно потому, что применение обратимо ровно
настолько же, насколько необратимо: оно перестраивает лифтовые секции, но
отменяется выбором другого варианта, а не отказом нажать кнопку. Второй шаг
защищал бы от того, от чего первый уже не защищает.

Выбранное значение при этом остаётся в поле: после перестройки секций иначе не
видно, какой конфигурацией их заполнили. Кнопка применения остаётся у карточки
— там она и есть действие карточки, а не подтверждение чужого выбора.

### 11. Списка «Ещё варианты» нет

Принято при осмотре блока в чате. Селект с остальными вариантами задумывался
как дешёвый способ не потерять хвост подбора. На экране он оказался хуже, чем
его отсутствие:

— в узкой колонке чата он занимает столько же места, сколько карточка, но
  несёт одну строку вместо трёх — сравнить по нему нечего;
— свёрнутый он не показывает **ничего**: ни интервала, ни комфортности, ни
  того, сколько вариантов за ним стоит, — пустое поле под подписью;
— применение из него необратимо перестраивает секции, а решение принимается
  по одному титулу, тогда как у карточки под тем же титулом стоят три пилюли.

Поэтому блок — только карточки. Хвост подбора не прячется в контрол, а просто
не показывается: сколько вариантов стоит предлагать, решает агент, отдавая их
в нужном порядке, а `topCount` ограничивает, сколько из них поместится.

Следствия: `moreLabel` из контракта убран — подписи не для чего; `topCount`
теперь означает не «сколько карточками из всех», а «сколько показать вообще».

## Risks / Trade-offs

- [Дрейф контракта ответа между агентом и каталогом] → типы объявлены здесь и
  экспортируются пакетом; в зеркальном change агента — требование импортировать
  их, а не зеркалить руками.
- [Блок «мигает» при быстрой правке N/A] → дебаунс 300 мс + состояние `stale`
  (старый список приглушён, а не снят).
- [Применение затирает уже введённые пользователем лифты] → это и есть
  осознанное действие пользователя (клик по варианту), но количество секций
  меняется молча — поэтому подпись кнопки говорит, что будет («Применить»), а
  `title` варианта несёт число лифтов.
- [Разъезд подбора в блоке и итога «Рассчитать»] → исключён общим ядром на
  стороне агента (та же цепочка `sweepCatalog*` и тот же `applyAutoDefaults`).
- [Второй компонент, привязанный к same-origin `/api/agent-resource`] →
  принятое ограничение каталога, уже действующее для lookup fetch-режима.

## Migration Plan

1. Релиз каталога с пропом и блоком — пассивен, пока агент не шлёт `recommend`.
2. Агент: ручка `/api/recommend` + `recommend` в props формы
   (change `recommend-resource`).
3. Оркестратор: `"lift-recommend": "/api/recommend"` в реестре remote-a2a.
4. Бамп каталога в spai-ui.

Откат на любом шаге безопасен: блок исчезает, форма остаётся рабочей.
