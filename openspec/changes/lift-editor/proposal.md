# LiftEditor: подбор лифтов одним сообщением

## Why

Агент elevator-calc собирает документ расчёта (здание + N лифтов) фазовым
мастером из плоских FormCard: вкладка «Лифт 1», «+ Добавить лифт», возврат на
«Здание» — каждый клик уходит в AG-UI-run и порождает новое сообщение, чат
фрагментируется, а пользователь ждёт сеть на действии, которое по сути
локально. Хуже того, табы — это `Button` вне FormCard, поэтому `nav:<screen>`
шлёт пустой `context`: несохранённые значения текущего экрана теряются при
переходе (обходной путь в агенте — `nav-merges-form-values` — лечит симптом,
но требует ещё одного round-trip).

Протокол a2ui раунд-трипа не требует: `ConstructionsEditor` уже доказал, что
вложенную структуру переменной длины можно редактировать целиком на клиенте и
отдать одним submit. Для лифтов такого компонента нет — в каталоге нет ни
повторяемых экранов-вкладок, ни переключения состава формы по значению поля.

## What Changes

- **Новый компонент каталога `LiftEditor`** (аддитивно, остаёмся в
  `CATALOG_VERSION` v2): вкладки «Здание» + «Лифт 1…N» (52941) или «Здание» +
  «Лифтовая группа» (34758), переключение вкладок, `+ Добавить лифт` и
  удаление лифта — локальным state'ом без единого AG-UI-run; один submit
  «Рассчитать» с полным документом в `context`.
- **Первичный переключатель — методика расчёта (ГОСТ), а не тип здания**:
  поле `methodField` («ГОСТ Р 52941-2008 (Жилое)» / «ГОСТ 34758-2021
  (Офис/Гостиница/Жилое)») локально перестраивает состав полей здания, полей
  лифта и сам список вкладок. Тип здания — обычное поле экрана «Здание» и
  существует только в ветке 34758, где он управляет рядами и таблицами
  (Прил. Е). Это возможно потому, что props несут конфиги ВСЕХ методик сразу —
  прямой аналог `typeConfigs[]` у `ConstructionsEditor`.
- **Схема** `packages/catalog-schemas/src/components/lift-editor.ts`: props —
  `methodField`, `methodConfigs[]` (по методике: `buildingFields[]`,
  `liftFields[]`, режим лифтов `per-lift` | `group`, правила зависимых
  значений), `method`, `building` (значения), `lifts[]` (значения), лейблы и
  имя action'а submit. Поля описываются `liftEditorFieldSchema` —
  расширением базового `formFieldSchema` FormCard (новой параллельной модели
  поля не вводим).
- **Поля со свободным вводом и подсказками ряда (`type: 'combo'`)**: Q,
  скорость, ширина дверного проёма вводятся произвольно, а нормативный ряд
  приходит из props как подсказка (`datalist`). Реальные каталоги содержат
  значения вне ряда ГОСТ, жёсткий `select` их запрещал.
- **Опции, зависящие от другого поля (`optionsBy`)**: ряды Прил. Е (ширина
  двери, скорость) различаются по типу здания — подсказки пересчитываются на
  клиенте при смене управляющего поля.
- **Зависимые значения на клиенте (`dependentRules[]`)**: смена `Vn` (52941)
  пересчитывает `h` и `t123`; в 34758 `Pk` подставляется по `Q`, а `tOst` — по
  тройке (тип здания, ширина двери, скорость). Сегодня это делает сервер в
  `mergeCalcDoc`/`form-args`, и без клиентского правила пользователь до
  submit'а видел бы значения от старого источника. Нормативных таблиц ГОСТ на
  клиенте по-прежнему нет: приходят готовые ряды значений.
- **Группировка необязательных полей (`advanced`)**: параметры со значениями
  по умолчанию сворачиваются в экспандер «Параметры по умолчанию», чтобы
  экран здания 52941 (8 полей, 6 из них — дефолты) начинался с того, что
  реально надо ввести.
- **Рендерер** `packages/catalog-react/src/renderers/lift-editor.tsx`
  (+ подфайлы вкладок/экрана/поля): паттерн FormCard — локальный state,
  наружу только submit.
- **Python-зеркало** `packages/catalog-python` + фикстуры valid/invalid/
  messages + TS/React/Python-тесты + превью в `apps/demo` (компонент
  разрабатывается и отлаживается там до интеграции с агентом).

Интерактивный макет поведения — `mockup.html` рядом с этим документом
(автономный HTML на фикстурах агента; UX согласован на нём).

## Capabilities

### New Capabilities

- `lift-editor`: контракт компонента — схема props, вкладки и повторяемые
  экраны лифтов на клиенте без раунд-трипов, переключение методики расчёта из
  предзагруженных конфигов, поля со свободным вводом и подсказками ряда,
  опции по значению другого поля, зависимые значения по одному и нескольким
  источникам, группировка параметров по умолчанию, submit одним action'ом с
  полным документом.

### Modified Capabilities

_(нет — поведение существующих компонентов не меняется; из `form-card.ts`
дополнительно экспортируется базовый объект поля до `refine`, чтобы
`LiftEditor` расширял его вместо копирования — сама схема FormCard и её
валидация остаются прежними)_

## Impact

- `catalog-schemas`: новый файл схемы + регистрация в `catalog.ts`
  (`componentDefinitions`), `constants.ts` (`CATALOG_COMPONENT_NAMES`),
  `index.ts` (export); аддитивный экспорт `formFieldBaseSchema` из
  `form-card.ts`. Изменение аддитивное — v2 сохраняется, публикация через
  `pnpm run export:public` (public/ коммитится).
- `catalog-react`: новый рендерер + регистрация в `catalog.ts`
  (`customComponents`).
- `catalog-python`: зеркальная Pydantic-модель + экспорт + parity-тест.
- `apps/demo`: страница-превью обеих методик (52941 с несколькими лифтами и
  34758 с группой) — основной стенд разработки этого change.
- Версия: minor bump синхронно (`pnpm run version:bump`) + CHANGELOG.
- Потребители: spai-ui поднимет `@ai37/a2ui-catalog-{schemas,react}`; агент
  elevator-calc эмитит компонент вместо цепочки FormCard и обрабатывает один
  submit — связанный change в `spai-elevator-calc-agent` (там же отмирают
  `nav:<screen>`, `add_lift`, `remove_lift`, `apply` как сетевые действия, а
  ряды Прил. А / Табл. Г.1 / Прил. Е разворачиваются в `dependentRules`).
- **Non-goals**: generic repeating-group как тип поля FormCard; dataModel/
  path-биндинг полей редактора; нормативные таблицы ГОСТ (Прил. А, Табл. Г.1,
  Прил. Е) как логика клиента; live-превью результата расчёта в редакторе;
  персист незасабмиченных правок при перезагрузке; таблица введённых данных и
  отчёт (остаются текстом от агента); кнопка «Справочники» внутри редактора
  (снята — редактор отправляет ровно один action).
